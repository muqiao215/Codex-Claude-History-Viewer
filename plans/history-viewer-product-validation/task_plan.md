# History Viewer — 正确性收口与首次使用验证

## Goal

让一个没有参与开发的人，仅依靠 README 就能安装启动 History Viewer，找到真实历史会话，理解有证据支持的交付结果，并导出可用于继续工作的交接材料。

## Background

2026-09-06 用户将新计划范围明确收敛到 History Viewer。项目取舍盘点作为方向输入：优先将已有能力做成可独立使用的作品，SpecMesh 只承担轻量连续性支持。本计划接续 004 升级和七项审查，不另建重写项目。

## Status

M1（七项复审）与 M2（真实浏览器验收）已完成，证据见 findings.md；当前 186 Python tests + 5 JS 套件通过。M3 陌生用户试用 pending（试用者由用户安排），M4 发布收口 pending。

## Requirements

- R1：用量可追溯到源记录，重复消息与缓存迁移不能造成虚增；不把 token 数称为费用。
- R2：简报保留失败证据及独有文件，聚合范围和任何截断必须明确。
- R3：会话、日期、来源切换后，预览、计划、叙事与导出内容属于当前上下文。
- R4：计划扫描真正限制读取及枚举工作量，源文件和上游数据库保持只读。
- R5：首次使用形成安装 → 找到会话 → 审计证据 → 交接导出的完整路径；空数据、未配置 AI、无用量来源有明确说明。
- R6：标准库后端、无构建前端、本地优先保持不变；可选 LLM 处理必须由用户显式触发。

## Non-goals

- 不新增 pi 等数据源、货币计费、云同步、多租户或强制 AI 分析。
- 不引入前端框架或另起后端重写，不为 app.py 拆分而拆分。
- 不扩展 SpecMesh Map、向量库、恢复平台或额外文档层级。
- 不继续增加 Star 候选；只有验收暴露具体缺口时才定向研究一个参考实现。
- 本计划不包含其他项目的开发、冻结或归档操作。

## Plan

### M1 — 七项修复独立复审（pending，阻断后续验收）

对比原审查场景、最新代码与测试；失败时先补能区分旧实现的回归测试，再做最小修复。

| 验收项 | 必须观察到的结果 |
| --- | --- |
| A1 Claude 去重 | 同 ID 重复、不同 usage 变体、无 ID 旧记录均有明确口径；固定源样本单独计算与解析/索引/简报一致；旧缓存重建后纠正数值 |
| A2 会话切换 | 用真实点击路径 A→B；B 的审计成功、404、报错及乱序响应均不残留 A 的预览/Plans；导出与可见内容一致 |
| A3 合并证据 | 高分完成 A + 低分失败 B 的重叠文件场景仍保留 B 的受阻信息和独有文件 |
| A4 完整聚合 | 41、210 会话以及置顶混合样本无遗漏/重复；超过 2000 的保护上限时全量概览仍正确，或接口和 UI 明示不完整，不能静默少算 |
| A5 缓存版本 | 全平台注册版本一致；临时旧索引重开证明实际回填，不只匹配源码中的版本数字 |
| A6 叙事上下文 | 日期切换、同日期换来源、旧 POST 慢返回及生成错误均不会显示旧叙事 |
| A7 扫描上限 | 用读取/迭代计数验证实际资源上限；不存在文件不占真实文件配额；大目录提前停止；边界文件、不可读文件不致请求崩溃 |

每项记录代码位置、复现命令、结果与剩余限制。完成标准：A1–A7 均有独立证据，无未解决 P1；影响核心闭环的 P2 必须先处理。

### M2 — 首次使用与真实浏览器验收（done 2026-09-06，遗留未验证项见 findings）

- 从 README 指定入口启动，分别检验干净环境/空数据和已有本地历史；记录实际运行版本与启动命令。
- 使用真实浏览器验证搜索、来源切换、审计证据跳转、Usage、Briefing、Plans，以及 Handoff 预览/富文本复制/两种文件下载。
- 在无 LLM 配置时完成核心流程；已配置模式只在获授权的测试中验证外部调用，不上传私有转录做演示。
- 检查六种代码主题、窄窗口、长标题、长路径、加载/失败状态和可键盘操作性；遵循 DESIGN.md，修复妨碍任务的呈现问题。
- 仅修复流程实际暴露的问题；界面用语应说明 usage 和简报按会话时间归属的真实统计口径。

完成标准：准备一份可重复的浏览器操作记录；检索 → 证据 → 导出闭环通过；示例数据不泄露真实私有内容。未验证的平台列为未验证。

### M3 — 小范围陌生用户试用（材料就绪，独立试用 pending，依赖 M2）

- 准备脱敏演示数据和一页任务说明；由用户安排至少一位未参与开发的试用者，不自动向外发送邀请。
- 试用任务：启动 → 找到指定会话 → 指出一项有证据的改动/失败 → 导出交接；记录耗时、卡点、求助次数和是否完成。
- 首轮作为基线；优先修复阻断任务的问题，再请试用者复走失败步骤。

完成标准：至少一名独立试用者在没有开发者逐步指导的情况下完成闭环，且没有未处理的阻断问题。若暂时无人试用，保持 pending，不用 Agent 自测替代。

### M4 — 发布收口（pending，依赖 M1–M3）

- 定向回归通过后跑全量 Python 和五个 JS 测试文件；新增测试按实际计数更新文档。
- README 只保留已验证能力、首次启动、缓存迁移和已知限制；校正 004 记录中的快照口径。
- 审核全部未跟踪文件，区分正式功能/测试/文档与无关计划、临时验证材料；生成可 review 的变更清单及发布说明草稿。
- 发布说明基于复验结果；未提交前不写假 commit hash。提交/发布按后续明确操作请求执行。

完成标准：可审阅的候选变更和发布说明就绪，验收证据与文档一致。准备完成与实际发布分别记录。

## Priority and Stop Rules

按 M1 → M2 → M3 → M4 推进，同时只处理一个主要验收缺口。先正确性，再可用性，最后外部试用；不以新增功能数量衡量进展。发现源格式变化、隐私外传或错误会话内容时，停止向下一里程碑推进并先定位。上限/降级不能伪装完整结果。

## Success

七项修复有独立证据；真实浏览器闭环通过；至少一位陌生用户独立完成任务；候选发布内容可复核。SpecMesh 的额外验证只检查新会话能否由 PROJECT 和本计划找到下一步，不另开实验。
